forbear log, entry 003: UI from JavaScript

2026-10-11

This is realtime layouting happening every single frame, running every single frame, without any caching running in both languages.

To properly support javascript, I've decided to run through Node.js. This doesn't mean I spawn a separate subprocess and then have to go communicating through a socket or IPC or whatever. It's in the same process by embedding Node.js and accessing the V8 memory mostly directly, which means we can keep the high bar for performance since most of the work is still done through Jai.

The central part of this is element definition, so let's talk about that first. Nodes are not defined in javascript here, as it might seem like it does. Nodes are all defines in jai, but the parameters all come from javascript. This also means, that, differently from React, elements are not values you can pass around and return. You just "define" the element and it gets pushed into the Node_Tree in jai.

This is both a blessing and a curse, I think the pros outweigh the cons particularly because this makes it more viable to rerun everything every single frame instead of just reacting when things change like React does. This means you can do animations and all sorts of weird things across frames since you have access to all, and each one of them.

The particular upside of this design is that users have access to all that they have in Node.js. They can use any libraries they're already used to, and they can use any Node APIs they might want.

To actually support this JSX flavour we're compilling this JSX with a TypeScript transformer that converts the element definitions into the open and close function calls. It also keeps track of source code locations so that it can replicate the keying that's done by the element macro in Jai.

If you've seen the other code samples, you can see that this is not actually quite different. The main difference is that jai doesn't render the elements directly, but rather calls this render_with_adapter.

The long term ideal is that every javascript application built with forbear will have this "escape hatch" of native code where they can just do about whatever they want. The reasoning for this is basically twofold:

  1. so that all javascript develoeprs start naturally learning and understanding more of the fundamentals without actually trying to learn them,
  2. and so that advanced users of the library can have full control of everything without having to give up their preferred convenience.

Among the details, we're also defining some .d.ts definitions so that the code feels comfortable for javascript developers, and many utilities that are defined using v8::FunctionTemplate from C++ and sometimes calling jai code as well.

layout

In other news, you can clearly see we also have layouting implemented! This has the following features:

  • fitting
  • growing
  • shrinking
  • text wrapping
  • fixed, minimum and maximum sizes
  • padding and margins
  • horizontal and vertical direction
  • justification on both axes
  • flow, fixed and relative placement

Overall it's actually not an extremely complicated algorithm, it's heavily based on Clay implemented with improvements to the old Zig version, that was written from scratch based on Nic's awesome YouTube video. It's only ~700 LOC on a single function.

The most interesting part about it is the fact that it runs on multiple passes over the entire Node_Tree and that's done for two reasons 1) because it makes the algorithm much simpler (as Nic explains in much more detail, and more depth than I can possibly do) and 2) because it really is faster to do that, than to retroactively update nodes, which would be the alternative.

The algorithm is also further made simpler because we use a single, flat array to store all nodes, which I call the Node_Tree, and since nodes are always inserted in the order parent -> children to iterate the entire tree we can literally just loop over it. If we want to go from children to parents, we can loop it in reverse, which makes this extremely cache coherent. In the long term, this layouting pass will be most likely optimized by a structure of arrays appraoch of doing things.

In the future, I will write an explanation around this algorithm and keep it updated so that users of the library can also debug issues, and understand layouting without having to read the code.

remaining fixes

Alongisde all of these changes, I've also gone through doing a bunch of improvements to the wayland client implementation and the way we define buffers so that this library can start actually creating things that someone would actually use. It's now not crashing when screnshotting, it's respecting the monitor's refresh rate through the frame event from the Wayland compositor and also is using a double buffer instead of just one.

Besides this, forbear now is based on

  • Before: the window rendered as fast as it could, with one buffer. Now it waits for the compositor's frame callback and uses two buffers.
  • Buffers come from gbm, with the formats and modifiers the compositor asks for.
  • Short list of fixes: resizing, uninitialized memory showing while resizing, the crash when taking a screenshot, answering xdg_wm_base pings, picking the compositor socket the way libwayland does.
  • The FPS counter, in both Jai and JavaScript, to check all of this.

smaller things

  • A flat pool for per-frame allocations.

  • You can now subscribe to new entries on the site.
